# 2026-11-20 - Attachments can sit on the project, carry their details, and the viewer stops cutting its lists

- **Nov 20 2026: three follow-ups on attachments, from the designer.** (1) "an attachment can be sitting just on a project level too"; (2) "just take a look at the attachment metadata"; (3) with a recording and a screenshot of the attachments viewer: "the info getting cut?" and "if there's more, we need to bring in the pattern for '2 more'".
  - **On the project (1).** An attachment's place was always a field of a record (field-notes-store: record, then field). The project is now a place too: `PROJECT_FIELD_KEY` ("project:Project") with the project's own id as the record. In "Upload attachments", one file: the record list starts with "BD-5039 Adelaide Hills Bushland Survey, Whole project", and choosing it asks for no concept. In the template, a row with Record ID and Concept ID both empty is on the project (the hints and the instructions say so; a record with no concept, or a concept with no record, is still a problem); the check table shows "Whole project". The Attachments tab lists them with the project as their place, and their button reads "Go to project" (the Overview tab). A project with no records can now take an attachment, so the dead end of the first version (a toast saying to add a record first) is gone for the single file.
  - **The metadata (2).** What the viewer shows about a file is optional: title, description, created, creator, licence, publisher, rights holder, which only the bulk template could set; a single file got the defaults. Both single-file forms (Upload attachments, and a record's Add attachment) now have "Add details", a link that opens the same optional fields with the template's own defaults in the hints (the file name, the project's publisher, CC-BY, the publisher). `AttachmentDetails` in `attach-fields.tsx`; the date is the design system's date field (2.11); the title's example is the template's own ("Looking north from the site marker", 2.18); the description has none, as no source gives one (0.3).
  - **The viewer (3).** The metadata list had a fixed 26rem cap with free space under it, so it ended mid-field with the Download button far below. It now takes the room the window has (`100dvh - 16rem`), scrolls past that, and has a fade at its foot saying there is more. The "Attached Resources" list showed 6 of 7 rows with the seventh cut; it now shows the first 5 and a secondary "Show 2 more" button with the ChevronDown (3.12, the product's pattern, as Explore's list does), revealing the rest; the open resource is always shown; it starts at 5 again when the viewer is reopened. Both lists are the shared `ArtefactLightbox`, so Explore's attachments tab gets the same.
  - **Verified.** Live (registered user, BioData Admin, Adelaide Hills): a single PDF on the project with a title, creator, description and CC-0 shows in the Attachments tab (count 8), the viewer reads "Project overview report", the creator, the date, and "Go to project" goes to Overview; the viewer at 1440 by 900, 846 and 1280 by 1000: the metadata list ends 16px above Download with the last field in view (scrolling with a fade at 846), Attached Resources shows 5 and "Show 2 more", pressing shows 7 and the button goes, opening the 7th shows all 7. The template check, run through the real `checkUpload` with a filled workbook: a row with neither ID is ready and on the project; a record with no concept is a problem ("Add the Concept ID."). Zero console errors. `tsc`, `eslint`, `check:contracts` clean. Not checked: a project-level attachment from the template in the browser (the zip path), audio or video review on a project, touch.
  - **Open, for the designer (0.4).** Whether a project-level attachment should also show on the Overview tab (it is listed in Attachments only); whether the details link should be open by default for the template-free path; whether a licence list beyond CC-0 and CC-BY is wanted. Not committed.
